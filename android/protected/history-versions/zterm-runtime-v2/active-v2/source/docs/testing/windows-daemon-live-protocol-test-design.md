# Windows daemon live protocol test design

## Scope

- Feature: `daemon.windows_wezterm_backend`
- Truth resources: `resource.terminal_backend -> resource.backend_session -> resource.wezterm_pane -> resource.mirror_store -> resource.transport_subscriber`
- Owner: WezTerm backend selection/control runtime. The smoke script is an observer only.
- Forbidden shortcuts: no tmux fallback, no direct mirror mutation, no broad process or pane cleanup.

## Lifecycle

1. Probe the configured Windows daemon `/health` endpoint.
2. Open one authenticated control WebSocket.
3. Create a uniquely named backend session through `tmux-create-session` compatibility wire semantics.
4. Request `session-open`, consume the returned ticket, then connect one session WebSocket.
5. Receive a structurally valid initial `buffer-sync` from the created pane.
6. Send a unique source marker through the live session transport and require a later decoded `buffer-sync` containing exactly that marker.
7. Close the created backend session through the daemon control protocol and require the following session list to omit it.
8. Close only the two WebSockets created by the run.

## Positive gates

- The daemon health response is reachable at the one configured endpoint.
- Session creation appears in the daemon session source.
- The initial target buffer has a valid revision, range, dimensions, and wire-line projection.
- Input sent through the session transport appears in a later target `buffer-sync`.
- Targeted close removes only the created session and pane.

## Negative gates

- A random missing session must produce `session-open-failed` or an explicit error; it must not create a pane.
- A missing or invalid auth token must fail connection when auth is configured.
- Backend failure must remain explicit. The smoke never retries against tmux or another endpoint.
- Cleanup failure fails the gate. The script must not use `pkill`, `killall`, process-wide termination, workspace-wide pane deletion, or an SSH cleanup bypass.

## Black-box comparison

The source marker is generated by the test and sent as real terminal input. The target is text decoded from the real daemon `buffer-sync` wire lines. Success requires exact marker presence in target buffer truth. Manual visual confirmation and JSON substring checks are not accepted.

## Known boundary

This gate proves the real daemon protocol, WezTerm pane, mirror projection, input echo, and targeted cleanup. It does not prove the packaged Windows desktop shell or Windows console Ctrl+C event semantics.
